# 持ち歩き用 起動プロンプト

Sasaki の機械（subagent 定義・knowledge・worktree 運用）を持ち込めない環境
（会社支給の Claude、使い捨てポッド、他人の PC 等）で、Sasaki の効きどころだけを
1 本のプロンプトに凝縮したもの。セッション冒頭にそのまま貼る。

## 貼るもの

```
これから一緒に開発する。以下のやり方で進めて。

1. 実装の前に必ず設計を出す。私が OK を出すまでコードは書かない
2. 設計の前に、使う API・メソッド・ライブラリが実在するか実際に確認する。
   記憶で書かない。確認できなかったものは「未確認」と明示する
3. 調査はサブエージェントに投げて、結果だけ返して。この会話に生ログを流さない
4. テストを書くときは、実装コードを読まずに設計だけから書く
5. 判断が要ること・分からないことは推測で埋めず、その時点で私に聞く
6. 「既存が壊れてる」「テストできない」「仕様外」と言う前に、実際に確認してから言う

再利用できる技術的な発見があったら NOTES.md に追記して。
汎用的な技術事実だけ書き、案件固有の情報は書かない。
```

## 補助

会社 repo を汚さずにローカル設定を置く（`.gitignore` と違いコミットされない）:

```
printf 'CLAUDE.md\n.claude/\nNOTES.md\n' >> .git/info/exclude
```

セッション終わりに持ち帰る:

```
今日の作業で得た、他の現場でも使える技術事実を 3 つまで、
汎用的な形に書き直して出して。案件固有の固有名詞は含めないで。
```

## なぜこの 6 項目か

Sasaki の各ロールが担う効果のうち、設定ファイルなしで再現できるものだけを残した。

| 項目 | 対応する Sasaki の仕組み |
|---|---|
| 1 | 承認ゲート（プランモードでも代替可） |
| 2 | Pre-design Research（Researcher） |
| 3 | subagent による文脈分離 |
| 4 | Reviewer のブラインドテスト生成 |
| 5 | エスカレーション |
| 6 | 否定的主張を独立検証なしで受理しない |

knowledge 蓄積と worktree 並列は、環境が許せば別途。ここには入れていない。
