## 設計doc に必ず含める

- **目的**（1-3行）: なぜ作るか
- **UI/UX**（該当時）: 画面レイアウト・コンポーネント構成・遷移。型付き言語なら DTO の Optional 性・enum・VM の public API・init まで
- **データモデル**: スキーマ・型定義
- **API/関数シグネチャ**: 入出力を具体的に
- **挙動仕様**: 「○○のとき△△」を #番号付きで網羅。← Reviewer はここからテスト生成
- **テスト基盤**: フレームワーク・テスト配置先（E2E なら chrome-devtools MCP 利用を明記）
- **不採用案**: 検討して却下した設計と理由（再検討ループ防止）

## 根本原則

- **導出値の手計算を doc に書かない。生成規則だけを書く。** 規則と手計算が矛盾したら規則が規範になり doc は errata になる。「この数値にすれば要件を満たす」は暗算のことがあるので、根拠に据えるなら不等式として自分で解き直し、解いた式を純関数として挙動仕様に置く。
- **識別子（symbol 名・API 名・フォント名・ファイル名）は書く前に実在を実測する。** ガイドラインが「filled variant を使え」と言っても、その variant が存在するかは別（存在しない symbol は無言で消える）。壊れるテストのファイル名は転記ミスで実在しないことがあるので `ls` する。
- **横断的変更（母数・型・命名規約）では影響を受ける既存テストを grep で機械的に洗い出してから移行リストを書く。** 目視列挙は漏れる。
- **「壊れるテスト N 件」はブリーフの予測でなく自分の設計で数え直す。しかも件数は設計で減らせる。** 既存関数に条件を混ぜず新関数を足す等で契約を保てば緑のまま。壊すのは減らせないものだけにし、減らせた理由を doc に書く（Reviewer が「なぜ緑か」を疑わずに済む）。
- **削除リストはワイルドカードで書き写さない。1 ファイルずつ import 元を grep して確定リストに展開する。** 同ディレクトリに現役 import されているファイルが混ざる。自分の設計が原因で孤児化するファイルは「消す/残す」がプロダクト判断なので勝手に消さず報告する（既に下りている裁定の結果 caller 0 になった残骸は実行してよい）。
- **切り分けプローブを設計に書いたら「成功時と失敗時で返り値が違うか」を必ず自問する。** 中間 proxy が応答を書き換えないかも確認する（書き換えるなら挙動仕様にも波及）。成功の証拠は横取りされうる 404 でなく 200 に置く。
- **検証を設計に組み込んだら「この検証が緑で、かつ本番が落ちる状態はあり得るか?」を自問する。** ポート公開プローブは in-container healthcheck の代理にならない、のような**経路の非対称**を 1 段掘る。「相手側の設定で回避する案」と「自分側を仕様に頑健にする案」が並んだら後者を採り、前者を理由付きで不採用案に残す。
- **スコープ外と切った既存コンポーネントに自分の設計の出力が流れ込むなら、その潜在バグは in-scope に昇格する。** 自分の新データが既存パイプラインを通るなら、そのパイプラインの暦・単位・丸め規則は自分の仕様の一部。
- **「additive か」はフィールド追加と enum 値追加で別問題。** enum 値追加は wire では additive でも旧クライアントの未知値フォールバックに落ちるので、配布済みビルドの表示を退行させうる。旧クライアントの挙動を実装で確認してから additive を名乗る。
- **逐語コードを doc に書くなら、その言語の型・隔離/並行性規則・レイアウトの取り付け先まで通してから書く。** 型検査を通すだけでは足りない。設計どおり書くとビルドが通らないと、そこから先は Developer の即興になる。

## 編集規律

設計doc の改訂は**追記でなく置換**（`/Users/amano/dev/Sasaki/CLAUDE.md` の「仕様マークダウンの編集規律」）。衝突節が参照する file:line は初回 Read でなく **doc 完成時点の main** で測り直す（リポは設計中も動く）。
