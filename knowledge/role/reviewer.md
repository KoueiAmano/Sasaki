# Reviewer の職業的習慣ノート

召集されたら最初に読む。**過去の自分（歴代 Reviewer）が実際に踏んだ穴**を書き溜める場所であり、予防的な網羅ルールではない。新しく踏んだら自分で追記・置換する（INDEX 対象外、再生成不要）。

**責務境界**: 恒久的な行動規範は agent 定義（`/Users/amano/dev/Sasaki/.claude/agents/reviewer.md`）が正典。この role note に書くのは、そこに載っていない**「自分が実際に踏んだ生の失敗ログ」だけ**。原則を二重管理しない。

このワークスペースは新設のためまだ実戦ログは無い。まずは以下の汎用原則から始め、実際に踏んだ穴で置き換えていく。

- **バグ修正系は negative control を標準にする。** 修正前に戻して落ちることを確認してから GREEN。落ちない負のコントロールは何も検証していない。
- **テストヘルパで DB 行や資格情報を捏造しない。** ヘルパがバグと同じ形を forge するとテストは実装に迎合して永久に緑になる。「そのテストは落ちうるか?」を自問する。
- **偽 RED / 全滅の疑いは実装でなく本番経路のプローブで切り分ける。** fixture の日付は本番の正規化規約に合わせる。
- **「ベースライン」と報告する前に known-failures 台帳と照合する。台帳に無い失敗は「未分類」と明記。** 未分類を残したまま GREEN を出さない。
- **assert は実装非依存の粒度で。** validation は status 中心（400）、redirect query は `url.Parse`、空状態は「キー存在 + 非 nil + len==0」。
- **「write が起きない」を「未配線」と即断しない。** best-effort のエラー握りつぶしと区別できない。帰属は観測レベルで書く。
- **env 由来の分岐はプロセス起動前に env を投入して検証する。** dev の `.env` が test に漏れることがある（regression と誤帰属しやすい）。帰属は negative control で決める。
- Bash で `&&` を使わない（heredoc 中の JS/Python でも発火）。共有 DB の全体回帰は `-p 1`。
